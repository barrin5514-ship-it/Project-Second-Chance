## Bounded vertical slice

- Authenticated private cases: create, list, read, edit a small user label/optional jurisdiction, and delete live cases with their documents using an explicit confirmation.
- Documents within an owned case: validated upload, metadata list/detail, authorized download of original bytes, and confirmed live deletion. Document replacement/moves, sharing and bulk export are out of scope unless separately specified; do not add endpoints implicitly.
- SQLite metadata and **separately encrypted blobs**, with sensitive case/document metadata also protected. Authenticated encryption through an established implementation, not a custom algorithm. No original upload filename, case label, court identifier or future derived content may silently become unencrypted identifying metadata.
- Local fictional inputs only. Keep accounts, root health/retry and optional Mira working. Case/document operations never call Nuance or another external service, grant AI consent or start microphone/camera.
- No OCR/text extraction, summaries, notice interpretation, legal claims, court queries, AI gateway, advocate/admin sharing, hosted deployment or real records. No inline PDF/image preview in this slice; controlled attachment download is sufficient.
- Live deletion belongs here; complete account deletion, backup retention, deletion-ledger/restore semantics and recovery rehearsal remain E1-S3. Do not present E1-S2 as proof of recoverability or permanent secure erasure. No new automatic backup feature or real-data activation ahead of that gate.

## Decisions to make concrete before coding

1. **Storage/schema and migration ADR.** Reuse installed SQLite stack with versioned migrations and ownership foreign keys. Identify non-sensitive routing/index fields permitted in plaintext (opaque IDs, owner relation, status, bounded technical counters) and protect user-entered/sensitive fields. Do not overwrite an existing auth DB to install tables. State how encrypted metadata is read/updated without plaintext journal/temp/log leakage.
2. **Encryption/key ADR.** Select maintained library/API, authenticated cipher/mode, fresh nonce generation, envelope version/tag validation and key reference. Bind ciphertext to resource context (owner/case/document IDs and version) using the chosen library's authenticated-data facility or equivalent supported design. Swapping a blob/metadata record across resources must fail authentication. A conventional library-backed AEAD design is a candidate; exact format is a proposal, not an owner-approved algorithm contract.
3. **Keys and lifecycle.** Use cryptographic randomness and separate document-encryption material from auth session secrets/password hashes. Select an explicit local key location outside Git and outside DB/blob/backup snapshots; prefer a separate configured directory rather than copying a master key beside data. Owner review must cover key loss/recovery assumptions. Do not create external key material as part of this handoff. During implementation, initialize keys only through the agreed fresh-store path; missing/corrupt/wrong keys with existing encrypted data must fail closed, never silently regenerate and orphan it. Programmatic key access is allowed; reading values into assistant context, browser code, logs or tracked examples is not.
4. **Upload/decoder ADR.** Proposed initial allowlist: PDF, PNG and JPEG, one file per request, with a measured small file cap (for example 5 MiB), bounded fields/parts, decoded dimensions/page/structure limits, concurrency and per-account quota. These numbers/formats require concrete workflow decisions; do not leave limits unbounded or pretend broad format support. Use maintained multipart/content-validation tools; extension, browser MIME and magic bytes alone are insufficient validation. Document unsupported/corrupt/encrypted documents and active-content handling; do not call local structural checks an antivirus guarantee. No paid/cloud malware scanner.
5. **Durable writes/deletion and errors.** Specify staging/pending/ready/deleting/error states, encrypted-only temporary storage, SQLite transactions plus atomic file publication/cleanup, crash boundaries and restart reconciliation. DB and filesystem do not form a single transaction. State when success is allowed, how incomplete work is hidden and how failed cleanup is retried/reported. Never return success for an incomplete save or deletion.

## Acceptance criteria and negative-path evidence

| AC | Required behavior and meaningful checks |
| --- | --- |
| P1 — Identity and ownership | Every case/document route enforces server-side identity, idle/absolute expiry, revocation and disabled-account rejection. Reuse/refactor an expiry-aware auth guard: the existing guard is local to `/api/auth/me`, so `req.isAuthenticated()` alone is insufficient for new routes. Derive owner from session, never a posted user ID. Two independent fictional accounts cannot list/discover/read/edit/upload-to/download/delete each other's resources through direct API requests, forged IDs or altered parent case IDs. Check both document and parent ownership; opaque IDs are not authorization |
| P2 — Private case lifecycle | Owner can create/list/read/edit a minimal case; persistence survives restart. Unknown IDs and another owner's IDs use consistent non-disclosing responses. Caller-supplied ownership/role/blob/key fields cannot reassign access. Validate fields, paging and request limits. No admin/list-all shortcut |
| P3 — Upload boundary | Require authenticated ownership and CSRF/Origin checks before expensive upload parsing or file publication. Test unauthenticated/expired/foreign-session upload, missing/invalid CSRF/Origin, no file, multiple files, forged MIME/extension, truncated/corrupt/unsupported formats, oversize stream, multipart field/part overflow and bounded decoder limits. Reject traversal, absolute paths, separator/Unicode tricks, CRLF filenames and symlink/junction escape attempts. No user filename/path may determine a storage destination |
| P4 — Encryption and confidentiality | Successful uploads leave only authenticated ciphertext and protected metadata at rest. Use distinctive fictional canaries to inspect test DB/WAL/journals, blob/staging files, responses and captured logs; document necessary plaintext exposure only in authorized response/memory. Never leave plaintext temp files or put sensitive values in filenames, URLs, audit/error messages. A plaintext document digest is not automatically safe metadata: protect content-derived fingerprints where identifying. No raw key/nonce misuse or predictable fallback |
| P5 — Integrity before disclosure | Authorized download returns byte-identical original content only after integrity/tag validation. Wrong/missing key, modified ciphertext/tag/nonce, truncated envelope or swapped owner/case/document context returns a generic failure with **zero unauthenticated plaintext released**. Do not stream `decrypt.update()` bytes before final authentication. No public static blob route, key-bearing URL or direct filesystem path. Use no-store, safe attachment disposition and nosniff; do not render uploaded content as HTML |
| P6 — Atomicity and storage faults | Exercise failed DB insert/commit, disk-full/write/rename/permission errors, locked SQLite, interrupted request/process and cleanup failure at explicit publication boundaries. No success with missing blob, ready row with incomplete ciphertext, orphan plaintext or deletion of another resource. Retry/restart reconciliation must be scoped to known managed IDs/states and stay within verified storage roots; no broad delete of a computed/unverified Windows path |
| P7 — Live deletion | Only the owner can delete a document/case; require CSRF and confirmation. Case deletion handles owned child blobs/metadata consistently. While cleanup is pending or fails, deny further download and show truthful pending/failed state; don't announce completion until required live removal is done. Repeated delete/retry is bounded and cannot revive content or remove unrelated files. No instant-erasure/backup-deletion promise; E1-S3 recovery/retention policy remains explicit |
| P8 — Restart and key loss | With the same external key/store, cases and original documents survive a clean restart and retain ownership/integrity. Missing/wrong/corrupt key or unavailable store fails closed without replacing keys or destroying ciphertext. Startup recovery of incomplete upload/deletion does not expose pending data or resurrect deleted live resources. This is persistence/fault evidence, not the full E1-S3 backup-restore rehearsal |
| P9 — Concurrent and revoked work | Test two accounts, overlapping upload/delete/download, duplicate submissions, and session expiry/logout/disable during a pending operation. Revalidate authorization at the selected commit/disclosure boundary; old UI requests cannot publish success or show another identity after session loss. Protect against stale session writes and stale response rendering; do not fix races with sleeps or automatic mutation replay |
| P10 — Usable protected UI | Minimal authenticated case list/detail, create/edit, file selection/upload status, metadata/download and explicit delete. Keyboard/narrow layout, expired-session return to sign-in, safe field errors, pending/failure/retry/cancel and no false saved badge. Explain supported formats/limits and fictional-only use. Keep retries honest after ambiguous writes; reconcile server state instead of silently duplicating an upload. Protect private routes at the API even if the UI is bypassed |
| P11 — Regression and review | Preserve auth's uniform registration response, request budgets, identity reconciliation, single-flight startup, all existing CSRF/Origin/Host tests, health and Mira behavior. Correct obsolete protected-upload-unavailable copy only once corresponding functionality is real, without implying extraction/legal/AI features. Run full maintained/API/browser/type/build/secrets/audit checks, preserved independent probes and new two-context private-file/integrity/fault regressions; report actual counts/exits, RED/GREEN/refactor, limitations and applicable risks |
