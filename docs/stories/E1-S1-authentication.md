## User value and authority

## Binding scope

- Implement local fictional-demo account creation, sign-in, authenticated current-account state and sign-out, with real server-side verification and session enforcement. Use two independent fictional accounts in acceptance tests.
- Use a maintained authentication solution and session library, Argon2id through an established library, library-managed opaque session cookies, server-side revocation/expiry and persistent SQLite account storage. Do not invent a password/session algorithm or treat Mira's prototype session map as account authentication.
- Collect only the minimum demo account identifier and password; no real personal details, SSNs, court records, documents or ages. The PRD's email-based schema is proposed: a fictional email such as `denise@example.test` is the default implementation proposal; no email delivery, ownership-verification claim or external account is authorized. If choosing another identifier, document the reason without changing approved product scope.
- Keep `/` public and fictional, preserve safe `/api/health`, and preserve the explicit opt-in `/mira` prototype. Account activity must not evaluate the Nuance SDK, send identifiers/credentials to it, start media or grant AI consent. Use separate cookie names/session boundaries for account auth and the Mira prototype.
- No case CRUD, uploads, encryption for private document workflows, extraction, AI gateway, legal answers, court adapter, hosted deployment, shared advocate/admin roles, payment, OAuth, MFA or email/recovery delivery in this slice. These remain future gates. Explain recovery limitations honestly; do not add a reset bypass or pretend identity verification.

## Required pre-code ADR/spec choices

Create an authentication/session ADR before behavior implementation. Verify current official docs, maintenance/security status, Windows/Node compatibility and resolved dependency versions. `express-session` is a candidate, not a complete authentication solution or an approved selection; separately identify maintained credential-authentication support, SQLite account/session adapters and Argon2id implementation. Reuse the modular monolith. Avoid default MemoryStore as the completed session-store design; do not custom-build a store merely to avoid evaluating maintained options.

Specify in the BMAD spec: identifier normalization/uniqueness; input/body limits; password policy and Argon2id work factors; generic failure semantics; session regeneration after login; persistence/restart behavior; idle and absolute expiries; revocation/logout races; CSRF/bootstrap route rules; rate-limit keys, windows and bounded cleanup; cookie options; required secret handling; safe error responses; and storage/config failure behavior. Exact durations, thresholds, routes and libraries are implementation proposals until recorded and reviewed through the workflow, not previously approved architecture decisions.

Suggested password baseline for the no-MFA demo: at least 15 characters, maximum at least 64, support passphrases without silent truncation or arbitrary composition rules, bounded resource use and local screening of common weak values. Use Argon2id with explicit measured parameters, at least an appropriate current OWASP baseline (for example m=19456 KiB, t=2, p=1), using library salts/verification. Do not silently substitute a weaker algorithm if installation fails. Do not send passwords to an external breach-checking service.

Cookies must be HttpOnly, with an explicit SameSite policy and bounded lifetimes. Any Secure=false exception is limited to documented loopback HTTP fictional development; never describe it as hosted security. Specify a fail-closed boundary for nonlocal/hosted configuration rather than making cookies work by disabling protection. Do not trust arbitrary forwarded headers or enable permissive CORS. Missing/invalid secrets or unavailable storage must never issue an authenticated session. Load ignored private settings programmatically without reading values into assistant context; preserve existing Nuance settings. Generate any new local secret programmatically into an explicitly ignored local path, never paste it into chat or tracked examples. No predictable fallback secret.

## Acceptance criteria and required negative paths

| AC | Observable behavior and evidence |
| --- | --- |
| A1 — Real account lifecycle | A fictional account is created in the selected SQLite account store; the password is never stored/logged/returned in cleartext. Sign-in verifies a real Argon2id hash, establishes a session and shows only that account's minimum profile. Sign-out revokes it server-side. Duplicate/invalid identifiers and wrong/nonexistent-account credentials use appropriately generic failures, without disclosing another account's existence |
| A2 — Session boundary | Anonymous, forged/tampered, expired, revoked and disabled-account sessions cannot retrieve authenticated account data. Login regenerates the session identifier; a pre-login/fixated identifier and a logged-out cookie cannot be replayed to authenticate. Server expiry is enforced even if a browser retains its cookie. Resolve a pending logout versus immediate-login race without sleeps or weakening revocation |
| A3 — Two-user isolation | Independent cookie jars for fictional A and B each return only their own account; client-supplied user IDs/roles cannot select or elevate another identity. No user-list/admin endpoint is added. No claim that this proves future case/document authorization: those negative-path tests belong to E1-S2 |
| A4 — Request protection | Account creation, login and logout have explicit cross-site/CSRF protections. Missing/foreign Origin, missing/mismatched CSRF, invalid method and malformed/oversized payloads are refused with generic no-store JSON, no paths/stacks/credentials. Distinguish ordinary same-origin bootstrap GET navigation (which may omit Origin) from mutating requests; do not repeat the Mira bootstrap bug. Use established library/framework primitives where available and test the chosen protection, not merely cookie flags |
| A5 — Abuse/resource limits | Test bounded registration/login attempts for both account-targeted guessing and source abuse, existing and nonexistent accounts, spoofed forwarded headers, invalid/very long input and repeated failures. Throttling produces an honest retry state and does not lock an account permanently or leak its existence. No fragile wall-clock timing assertions as evidence of enumeration resistance |
| A6 — Persistence/faults | Test account persistence across a clean app restart using temporary SQLite fixtures. State whether sessions persist or expire at restart and test it. Expired/revoked sessions remain invalid across the selected lifecycle. Missing/malformed secret, unavailable/locked store, failed insert/hash/session-save or failed logout must not produce a false authenticated/signed-out success. Use injected failures at real boundaries; no browser-only auth or success-before-save |
| A7 — Usable local UI | Keyboard-accessible labeled create-account/sign-in forms, password-manager/autocomplete-friendly controls, field validation, generic auth failure, pending state, throttled/retry state, signed-in account and logout. Handle stale/in-flight responses and expired sessions without showing a previous account. Browser tests cover two accounts in separate contexts, logout/replay and narrow viewport. Never put credentials/session tokens in URLs or localStorage |
| A8 — Honest foundation/Mira preservation | Update the old exact “accounts ... not available yet” copy and its assertions once accounts actually work; keep `Project Second Chance`, `Fictional data only`, No False Hope, and protected-upload unavailability. Do not preserve misleading copy for an old test or weaken unrelated safeguards. Root health/retry retains its bounded timeout and sanitized errors; Mira keeps camera-off, explicit Start, no-key automated tests and independent media/SDK/restart probes |
| A9 — Evidence and secrets | Runtime DBs, journals/WAL/SHM, sessions and keys remain ignored. No fixture or snapshot contains real credentials; `.env.example` has placeholders only. Audit new production dependencies and record blockers. ADR/threat model/README/spec explain implemented controls and missing recovery/private-storage/hosted capabilities. Each behavior has actually observed RED → GREEN → regression evidence with requirement/risk links; library use is not a substitute for testing app boundaries |
| A10 — Independent gates | Run maintained unit/API/integration, browser, type/build, secret checks and production audit after implementation, plus preserved independent probes where available. Report actual commands/exits/counts/limitations. Save builder evidence and stop for fresh Codex independent testing, actual Claude review and owner merge approval. No self-certification of those roles |
