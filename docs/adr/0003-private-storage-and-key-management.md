# ADR-0003 — Private case/document storage and key management

- Status: **proposed by the builder (DeepSeek)** for E1-S2. This records implementation choices, not new architecture approval or production security certification.
- Date: 2026-11-24. Branch: `feature/e1-s2-private-documents`, based on local `main` `e2edea5a11ba250b881449acaa951844e38abba0`.
- Binding constraints: AD-01/02/03/06/09/10; FR-02/03/05/06/07; NFR-01/02/04/07/13/14/18/19/22. E1-S3 retains full deletion/retention/backup/restore; no real records.

## Context

E1-S2 adds owner-isolated case CRUD and encrypted documents. SQLite metadata and encrypted blobs are separate stores, so DB and filesystem cannot share one transaction. User-entered metadata (case label, jurisdiction, original filename, content hash) must not appear in plaintext at rest.

## Decisions

### D1 — One SQLite database, versioned migrations, ownership keys

- Reuse the existing auth SQLite database at `runtime/psc-auth.sqlite`; do not overwrite it. A `schema_migrations` table applies versioned additive migrations.
- Tables:
  - `private_cases(id TEXT PK, owner_id TEXT NOT NULL REFERENCES users(id), status TEXT NOT NULL, metadata BLOB NOT NULL, metadata_version INTEGER NOT NULL, created_at INTEGER NOT NULL, updated_at INTEGER NOT NULL)`.
  - `private_documents(id TEXT PK, case_id TEXT NOT NULL REFERENCES private_cases(id), owner_id TEXT NOT NULL REFERENCES users(id), status TEXT NOT NULL, blob_name TEXT NOT NULL UNIQUE, blob_version INTEGER NOT NULL, metadata BLOB NOT NULL, metadata_version INTEGER NOT NULL, ciphertext_bytes INTEGER NOT NULL, created_at INTEGER NOT NULL, updated_at INTEGER NOT NULL)`.
  - Indexes on `(owner_id, created_at)` and `(case_id, created_at)`; foreign keys enabled.
- Plaintext columns are limited to opaque IDs, owner/case relations, lifecycle status, random managed blob name, version counters, ciphertext byte size and timestamps. No label, jurisdiction, original filename, MIME, plaintext digest, user path or content is a plaintext column.
- Encrypted metadata JSON:
  - case: `{label, jurisdiction|null}`;
  - document: `{originalName, mimeType, size, sha256}`.
- Metadata is re-encrypted with an incremented `metadata_version` on edit. AAD binds version, owner/case/document IDs and metadata kind, so a record/metadata swap fails authentication.

### D2 — Key material and separation

- A 32-byte master key is generated by `crypto.randomBytes(32)` once into `<keyDir>/master-key.json` (`version:1`, random `keyId`, base64 key), mode 600 where supported. Default `keyDir=runtime/keys`; default `dataDir=runtime/private`. Both are git-ignored and outside the browser/DB. Tests inject isolated temporary dirs and never read real keys.
- The auth session secret and password hashes remain separate; no reuse.
- Master key is expanded with HKDF-SHA256 into independent 32-byte metadata and blob keys using a fixed app salt and distinct info strings. Envelope `keyId` records the master-key generation.
- Missing/corrupt/wrong keys with existing private data fail closed. A key is created only for a fresh store with no private records and no managed blobs; startup never silently replaces a key. A key-check envelope in SQLite is authenticated by the derived metadata key and compared with the current keyId, so a substituted key fails before private data is used. Key loss means the encrypted data is unrecoverable by this app.
- A database with no key-check record is accepted only when it has no private rows and there are no managed blobs. Otherwise startup fails closed, so a reset or mismatched database cannot cause reconciliation to delete ciphertext it does not know about. A database restored from an older copy still has its key check, and blobs newer than that copy would be removed as orphans: E1-S3 restore design must handle this. *Review change, 2026-11-24.*
- No key backup/recovery rehearsal is implemented here; that remains E1-S3. No key value is logged, returned, placed in a URL, committed or read into assistant context.

### D3 — AEAD envelope

- AES-256-GCM through Node's maintained `node:crypto` (`createCipheriv`/`createDecipheriv`), fresh random 12-byte nonce per seal, 16-byte auth tag.
- Binary envelope: magic `PSC1`, format version, keyId length + bytes, IV, tag, ciphertext. A parser validates lengths/version before decrypt.
- AAD context strings:
  - metadata: `psc1|meta|<ownerId>|<caseId>|<recordId>|v<metadataVersion>`;
  - blob: `psc1|blob|<ownerId>|<caseId>|<documentId>|v<blobVersion>`.
- Decrypt calls `final()` before any plaintext is returned; a wrong key, tampered/truncated envelope, swapped ID/version or wrong AAD produces a generic failure. No streaming plaintext before authentication.
- SHA-256 of original bytes is stored only inside encrypted metadata; it is verified after decrypt for download integrity.

### D4 — Managed blob layout and durable publication

- Blob bytes live only as ciphertext at `<dataDir>/blobs/<first2>/<random blob_name>.psc`; staging is `<dataDir>/staging/<random>.part`.
- No user filename/path determines a destination. Blob names are server-generated base64url IDs.
- Upload sequence:
  1. validate/auth/quota and encrypt in memory;
  2. write ciphertext to staging with mode 600 and fsync;
  3. insert `private_documents` row `status=pending` in a transaction;
  4. rename staging to final, fsync the directory;
  5. update row to `ready` and return success.
- Any failure before `ready` removes the staged/final file and row where possible. No success is returned for an incomplete publication. A crash between steps leaves a pending row/orphan ciphertext for scoped reconciliation.
- Startup reconciliation removes staging files, pending document rows/blobs and orphan managed blob files, and marks ready documents with missing blobs as `error` (never exposes or deletes unrelated files). Deletion/cleanup is restricted to verified managed roots and server-generated names. Reconciliation removes only files with server-generated names in real directories; it does not follow links or junctions and leaves other files in place. Pending rows are hidden from list and detail.

### D5 — Live deletion and status

- Document delete: require owner/CSRF/confirmation, set `deleting`, unlink the managed ciphertext, delete the row; only then report success. Failure marks `error`, keeps downloads denied and allows bounded retry.
- Case delete: mark case `deleting`, delete each owned document/blob and row, then case row. Partial failure marks `error`; retry resumes from known IDs. Downloads/list metadata for deleting/error cases are denied or hidden honestly.
- Repeated deletion is idempotent for already-removed live content; it cannot revive content or delete unrelated files. No permanent-erasure or backup-deletion claim; E1-S3 owns retention/recovery.

### D6 — Authorization boundary

- Reuse the auth session and exact loopback Origin/Host/CSRF protections. Export an expiry-aware `requireAuth` from auth: it checks Passport authentication, session `createdAt` absolute lifetime and disabled/missing deserialize behavior; idle expiry is enforced by the session store.
- The recheck before upload publication re-reads the stored session and the account, because the request's own copy does not show a later logout or disable. Downloads require the parent case to be `ready`. All `/api/cases` responses are `no-store`.
- Every private route derives owner from `req.user.id` only; posted `ownerId`, `role`, `blobName`, `key` or path fields are ignored/rejected. Both document and parent case ownership are checked with a join; unknown/foreign IDs return the same generic 404.
- No list-all/admin shortcut.

## Consequences / limits

- DB+filesystem cannot be atomic; reconciliation covers known crash windows but is not a distributed transaction.
- No backup/restore, secure-erasure guarantee, hosted key store, HSM or multi-process quota lock.
- Concurrent upload/delete can race at the DB/filesystem boundary; authorization is rechecked at the commit/disclosure boundary, but this slice does not claim serializable cross-store transactions.
- This is local fictional-demo security evidence, not production certification.
