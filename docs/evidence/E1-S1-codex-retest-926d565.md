## F4 — P2: account bootstrap can pair one response's token with another response's cookie

Locations: `apps/web/src/main.tsx:13–18`, `apps/web/src/account/AccountPage.tsx:80–101`, `apps/web/src/account/accountClient.ts` CSRF fetch, `apps/server/src/auth/auth.ts:248–250` session-backed CSRF response.

The Vite-served account page is wrapped in StrictMode, so initial effect setup/cleanup/setup starts two cookieless CSRF requests. Each server response creates a distinct session/cookie. React's active-effect guard chooses the newer effect's token, but cannot stop the browser processing Set-Cookie from an older ignored response. If that cookie arrives last, a valid registration carries mismatched session/token and is correctly rejected with 403. This is a fail-closed availability/initialization defect, not a CSRF bypass.

Observed in the unmodified 50-test browser run: desktop lifecycle and replay tests both failed at initial create-account acceptance (48 others passed). Their screenshots showed filled forms with no acceptance message. The natural-run partial trace's completed network entries showed two cookieless CSRF 200 responses with distinct cookie digests, followed by register 403 and reconciliation requests. Ordinary ZIP reading failed because trace collection was interrupted during the reported teardown timeout; Codex recovered only completed local entries programmatically and printed route/status/digest metadata, never raw cookies/tokens. Not all original response bodies were recoverable, and isolated reruns subsequently overwrote the default test-results directory.

A new independent probe at `.setup/codex-auth-cookie-race.spec.ts` delays the first **real** CSRF response before fulfilling it. The first run reproduced the missing acceptance message. A second, instrumented run checked registration status and compared tokens/cookies in memory without logging values. It observed exactly this non-secret metadata: `{initialResponses:2, tokenFromResponse:2, cookieFromResponse:1, status:403}`. The expected 201 assertion failed. That confirms the cookie/token mismatch beyond inference from the incomplete original trace. No mocked session/token algorithm or application change was used. The injected 700 ms delay is network fault injection, not a proposed sleep-based product fix.

[React's StrictMode documentation](https://react.dev/reference/react/StrictMode) describes extra development effect execution. The new probe's own config uses the existing real dev servers, absent provider credentials and Chromium. The original eight-probe hashes above remain unchanged.
